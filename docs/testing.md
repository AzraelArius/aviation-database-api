# Testing and CI

## Scope and isolation

All original 54 regression cases remain. They cover purchases by class, exact
capacity, API validation and errors, check-in, SQL constraints, rollback,
parameterized names, competing pools/direct writes and materialized-view analytics.
New tests cover atomic migrations, checksum/history rejection, once-only and
competing initialization, seed rollback, API size/method/rate-limit errors,
configuration validation and explicitly stale higher-isolation transaction snapshots.

`TEST_DATABASE_URL` must name an isolated database ending in `_test`. Every database
fixture creates a random schema and removes that schema in `finally`. Demo data,
test data and original academic data are separate. The role needs schema creation
privileges; concurrency tests inspect lock waits for its own PostgreSQL sessions.
The default test profile is sequential. SQL test fixtures use fixed data relative
to the database clock so future-flight behavior does not depend on a calendar date.

Integration cases skip when `TEST_DATABASE_URL` is absent. A skipped suite is not
proof that integration tests pass. CI always supplies and initializes PostgreSQL.

## Commands

After `pip install -e '.[test]' -c requirements.lock`:

```bash
createdb aviation_test
export TEST_DATABASE_URL='dbname=aviation_test'
ruff check .
python -m compileall -q src scripts tests wsgi.py
bash -n scripts/entrypoint scripts/start
python -m pip check
pytest -q tests/test_migrations.py tests/test_api_edges.py
pytest -ra --cov=aviation_api --cov=scripts --cov-branch \
  --cov-report=term-missing --cov-report=xml:reports/coverage.xml \
  --cov-report=html:reports/htmlcov --junitxml=reports/junit.xml
```

Reports and generated bytecode are ignored by Git. Coverage is measured for Python
application/setup code with branches; PostgreSQL function bodies are tested through
real writes, not included in Python line coverage. There is no percentage gate.
Measured results and remaining gaps are recorded in [verification.md](verification.md).

One regression deliberately simulates legacy corruption by temporarily disabling
a layout trigger **inside its disposable test schema** to verify a controlled
no-seat response. Normal initialization and demonstration seeding never disable
or weaken integrity rules.

## GitHub Actions

The workflow triggers on pushes to `main`, pull requests and manual dispatch. It
uses Ubuntu 24.04, Python 3.12, an isolated PostgreSQL 16.15 service with a readiness
check, constrained editable installation, migrations, deterministic SQL fixtures,
Ruff/static checks, pytest with coverage, and uploaded test/coverage reports.
Repository permissions are `contents: read`; checkout credentials are not persisted.
The development service credentials are explicit throwaway placeholders, not secrets.
No deployment job or external database is used.

Supported action versions were checked against the maintainers' documentation:
[checkout](https://github.com/actions/checkout),
[setup-python](https://github.com/actions/setup-python), and
[upload-artifact](https://github.com/actions/upload-artifact).
The service follows GitHub's [PostgreSQL service-container guidance](https://docs.github.com/en/actions/tutorials/use-containerized-services/create-postgresql-service-containers).
Terminal/XML/HTML coverage outputs follow [pytest-cov reporting](https://pytest-cov.readthedocs.io/en/latest/reporting.html).

The workflow has not been executed on GitHub. Equivalent install, initialization,
fixture and test commands were run locally; hosted runner execution and artifact
upload still require a future GitHub run after publication is approved.
